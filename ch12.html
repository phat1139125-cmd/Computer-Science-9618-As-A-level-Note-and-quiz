TOPIC 01 · §12.1
Program Development Life Cycle (PDLC)
STAGES · DOCUMENTS PRODUCED · PURPOSE
PURPOSE OF PDLC

Makes projects easier to plan and manage. Clear deliverables produced at end of each stage. Allows prototypes to be shown to client.

STAGEWHAT HAPPENSDOCUMENTS PRODUCED
1. AnalysisDeveloper discusses requirements with client. Current system examined.Problem definition, client requirements, ER diagrams, current system docs
2. DesignAlgorithm and UI designed. Data structures and language chosen.Identifier table, algorithms/pseudocode, UI mockups, structure charts
3. CodingProgram written from design. Syntax errors may occur.Source code
4. TestingProgram tested with various data. Errors corrected.Trace table, test plan, test results
5. MaintenanceProgram updated/improved after release.Updated documentation
TOPIC 02 · §12.1
Waterfall Model
LINEAR · SEQUENTIAL · BENEFITS · DRAWBACKS
WATERFALL MODEL

Each stage completed fully before the next begins. Linear progression. Full documentation at each stage. Client involved mainly at start and end.

✅ Waterfall Benefits
  • Easy to manage — stages don't overlap, completed one at a time
  • Each stage has clear, specific deliverables
  • Detailed documentation of entire project
  • Little room for client to change mind — smoother development
  • Client has clear idea of finished product
❌ Waterfall Drawbacks
  • No working program until late in lifecycle
  • Slower to market than competitors
  • Difficult to cope with changes in requirements
  • Needs high involvement from client at start
  • Client only sees product at very end
TOPIC 03 · §12.1
Iterative & RAD Models
ITERATIVE · RAPID APPLICATION DEVELOPMENT · COMPARISON
Iterative Model
  • Development cycle repeated until full program built
  • Split into repeated stages/sprints
  • Working programs produced early in cycle
  • Easier to test and debug incrementally
  • Flexible to changes in requirements
  • Customer involved at each iteration
❌ Iterative Drawbacks
  • Whole system must be defined at start for clear stages
  • Client can easily change requirements often
  • More planning needed to section project clearly
RAD Model
  • Modules developed in parallel as prototypes
  • Minimal planning — allows changes
  • Flexible development process
  • Used for time-critical development
  • Client involved throughout all stages
  • Multiple areas worked on simultaneously
❌ RAD Drawbacks
  • Difficult to estimate cost/time needed
  • Client can change requirements often
  • Documentation often omitted
  • Requires skilled developers working in parallel
FEATUREWATERFALLITERATIVERAD

Client involvementStart and end onlyEach iterationThroughout all stages
FlexibilityLow — hard to changeMedium — per iterationHigh — minimal planning
DocumentationExtensiveGoodOften omitted
Best forWell-defined, stable requirementsRequirements may evolveTime-critical, fast delivery
TOPIC 04 · §12.2
Program Design Tools
STRUCTURE CHARTS · STATE-TRANSITION DIAGRAMS
Structure Chart — Purpose
  • Shows module relationships
  • Shows how problem is broken down into modules
  • Determines whether module is function or procedure
  • Shows parameters passed between modules
Structure Chart — Symbols
  • Curved arrow — iteration/looping
  • Downward arrow — result passed to next stage
  • Upward arrow — more work required on previous stage
  • Rectangle — module/procedure
  • Diamond — selection/condition
State-Transition Diagram
  • Shows states a system can be in
  • Arrows represent transitions between states
  • Each arrow has format: input | output
  • X symbol signifies start state
  • Used to document algorithm behaviour
TOPIC 05 · §12.3
Testing Methods
ALPHA · BETA · WHITE-BOX · BLACK-BOX · INTEGRATION · STUB · WALKTHROUGH
Alpha Testing
  • Carried out by development team
  • Check program works as intended
  • Identify and address errors before release
Beta Testing
  • Carried out by small group of potential users
  • Users check program works as intended
  • Identify errors and provide feedback/suggestions
  • Problems addressed before program is sold
White-box Testing
  • Tests logic of ALL possible paths through code
  • Detailed testing of how each procedure works
  • Tester has access to source code
Black-box Testing
  • Tests a module's inputs and outputs only
  • Tester has NO access to source code
  • Tests if correct output produced for given input
Integration Testing
  • Individual modules tested during development
  • Modules combined and tested as a whole program
  • Tests that modules work correctly together
Stub Testing
  • Used when program has incomplete/erroneous modules
  • Faulty modules replaced by dummy modules
  • Dummy modules return known/expected result
  • Output statement shows they were called
Walkthrough Method
  • Program checked by creating a trace table
  • Goes through code one line at a time
  • Records variables as they change
  • Error indicated when variable gets unexpected value or unexpected path taken
⚡ ALPHA vs BETA  Alpha = development TEAM tests before release. Beta = small group of POTENTIAL USERS test before release. Both find errors — beta also collects user feedback.
TOPIC 06 · §12.3
Error Types & Test Data
SYNTAX · LOGIC · RUNTIME · NORMAL · ABNORMAL · BOUNDARY
Syntax Error
  • Code breaks rules of the programming language
  • Examples: missing ENDIF, misspelled keyword, wrong brackets
  • Detected by translator (compiler/interpreter)
  • Program with NO syntax errors: obeys grammar of language and will run without flagged error
Logic Error
  • Program runs but produces incorrect output
  • Algorithm design is flawed
  • NOT detected by translator
  • Examples: wrong formula, incorrect condition, off-by-one in loop
Runtime Error
  • Program crashes during execution
  • Program performs an invalid operation
  • Examples: division by zero, accessing invalid memory, infinite loop
TEST DATA TYPEDESCRIPTIONEXPECTED RESULT
NormalValue within acceptable rangeShould be ACCEPTED and processed correctly
Abnormal / ErroneousValue outside acceptable range or wrong typeShould be REJECTED with appropriate message
Boundary / ExtremeMinimum or maximum acceptable valueShould be ACCEPTED (tests edge of valid range)
⚡ TEST DATA EXAM  For a field accepting ages 1–100: Normal = 25 (accepted). Abnormal = -5 or 200 (rejected). Boundary = 1 and 100 (both accepted). Always give specific values in context of question.
TOPIC 07 · §12.3
Types of Maintenance
CORRECTIVE · ADAPTIVE · PERFECTIVE
TYPEWHEN USEDEXAMPLE
CorrectiveProgram does not operate as expected / contains a bugFix crash when user enters letters in numeric field
AdaptiveAccommodates legislative/user requirement changes; new technology availableUpdate for new tax law; support new operating system
PerfectiveChanges made to improve program after it has been releasedAdd new feature users requested; improve performance
⚡ MAINTENANCE MNEMONIC  CAP = Corrective (fix bugs), Adaptive (adapt to changes), Perfective (improve/perfect). Corrective = something BROKEN. Adaptive = external CHANGE needed. Perfective = make it BETTER.

QUESTION 02
State the difference between a syntax error and a logic error. [2]

MARK SCHEME

  • Logic error: program runs but produces incorrect output — algorithm design is wrong, NOT detected by translator (1)
● EASY
QUESTION 03
A program accepts exam scores between 0 and 100. State suitable normal, abnormal and boundary test data. [3]

MARK SCHEME

  • Normal: any value between 1 and 99 e.g. 55 — should be accepted (1)
  • Abnormal: value outside range e.g. -1 or 150 or "abc" — should be rejected (1)
  • Boundary: 0 and 100 — should be accepted (both values tested) (1)
Examiner: Must give specific values for each type. "A large number" = 0. Always state what should happen.
◆ STANDARD
QUESTION 04
Compare the waterfall and iterative development models. Give three differences. [6]

MARK SCHEME (any 3 × 2)

  • Waterfall: each stage completed before next begins / Iterative: stages repeated in cycles (1) — waterfall is linear, iterative is cyclical (1)
  • Waterfall: no working software until late / Iterative: working software produced at end of each iteration (1) — iterative gets to market faster (1)
  • Waterfall: client only at start and end / Iterative: client involved at each iteration (1) — iterative more flexible to changing requirements (1)
  • Waterfall: extensive documentation / Iterative: documentation per iteration (1)
◆ STANDARD
QUESTION 05
Describe the difference between alpha testing and beta testing. [4]

MARK SCHEME

  • Alpha: carried out by the development team (1)
  • Alpha: checks program works as intended before release to public (1)
  • Beta: carried out by a small group of potential/end users (1)
  • Beta: users provide feedback and identify errors; problems fixed before product sold (1)
◆ STANDARD
QUESTION 06
Explain the three types of software maintenance. [6]

MARK SCHEME (each type × 2)

  • Corrective: used when program does not work as expected / contains a bug (1) — fixes errors discovered after release (1)
  • Adaptive: accommodates legislative or user requirement changes (1) — allows program to be updated when new technology/laws require it (1)
  • Perfective: changes made to improve the program after release (1) — adds new features or improves performance based on user feedback (1)
◆ STANDARD
QUESTION 07
Explain the difference between white-box and black-box testing. [4]

MARK SCHEME

  • White-box: tester has access to source code (1) — tests all possible paths through the program logic (1)
  • Black-box: tester has NO access to source code (1) — only tests inputs and expected outputs (1)
★ CHALLENGE
QUESTION 08
A development team is building a hospital patient management system. Requirements may change as doctors use the system. Speed of delivery is critical.
Justify which development model (waterfall, iterative, or RAD) is most suitable. [4]

MARK SCHEME (RAD or Iterative — both acceptable with justification)

  • [RAD] Modules developed in parallel (1) — faster delivery as speed is critical (1)
  • [RAD] Minimal planning allows requirements to change easily (1) — doctors can change requirements as they use the system (1)
  • [Iterative] Working software produced at each iteration (1) — doctors can provide feedback early on real software (1)
  • Waterfall not suitable — no working software until end; requirements likely to change (1)
Examiner: Named choice + reason + link to scenario. "RAD is suitable" = 0. "RAD is suitable because modules are developed in parallel, meaning the system can be delivered faster which is critical for the hospital" = 2 marks.
★ CHALLENGE
QUESTION 09
Describe what stub testing is and explain when it is used. [4]

MARK SCHEME

  • Stub testing: incomplete or erroneous modules replaced by dummy modules (1)
  • Dummy modules return a known/expected result or output a message to show they were called (1)
  • Used when a program contains modules that have errors or are not yet complete (1)
  • Allows the rest of the program to be tested even when some modules are not ready (1)
