TOPIC 01 · §6.1
Security, Privacy & Data Integrity
DEFINITIONS · WHY DATA MUST BE KEPT SECURE
Data Security
  • Protects data against loss/corruption
  • Ensures recovery is possible
Data Privacy
  • Ensures data is protected against unauthorised access
Data Integrity
  • Ensures consistency/accuracy of data
  • Checks data is up to date
  • e.g. validation/verification rules, cascading update/delete
REASONWHY KEEP DATA SECURE
Data securityProtect against someone deleting, modifying or stealing data
System securityProtect against malware installation or system damage
TOPIC 02 · §6.1
Threats to Computer Systems
VIRUS · SPYWARE · HACKING · PHISHING · PHARMING
🦠 Virus / Malware
  • Malicious software that replicates itself
  • Downloaded/run without user knowledge
  • Runs in background
  • Can damage/delete/corrupt data
  • Does NOT send data out of computer
🕵️ Spyware
  • Malicious software
  • Downloaded/run without user knowledge
  • Secretly records user data/actions
  • Sends data/activity logs to third party
  • Does NOT replicate itself
💻 Hacking
  • Illegal/unauthorised access
  • Used to delete/damage/collect data
  • Done with malicious intent
📧 Phishing (requires user action)
  • Email pretends to be from official body
  • Persuades user to disclose private information
  • Redirects to unofficial website
  • REQUIRES user to click/act
🌐 Pharming (automatic)
  • Automatically redirects user to false/fake website
  • No user action required
  • Prevention: check URL validity, ensure HTTPS
THREATREPLICATES?SENDS DATA OUT?USER ACTION NEEDED?
Virus✅ Yes❌ NoSometimes (download)
Spyware❌ No✅ YesSometimes
Phishing❌ No✅ Yes (user discloses)✅ Yes
Pharming❌ No✅ Yes (fake site)❌ No (automatic)
⚡ PHISHING vs PHARMING  Phishing REQUIRES user action (click email link). Pharming is AUTOMATIC — user just visits website and gets redirected. This distinction = exam mark.
TOPIC 03 · §6.1
Protection Methods
FIREWALL · ANTI-MALWARE · ENCRYPTION · ACCESS RIGHTS · DIGITAL SIGNATURES
🔥 Firewall
  • Monitors incoming and outgoing traffic/packets
  • Compares packets to criteria (whitelist/blacklist/blocked IPs)
  • Blocks/rejects packets that don't match criteria
  • Accepts packets that do match
🔒 Encryption
  • Converts data into cipher text
  • Cannot be understood if intercepted without decryption key
  • Protects data in transit and at rest
👤 Access Rights
  • Give certain users access to different elements
  • Uses different accounts/logins with different access levels
  • Specific views can be assigned
✍️ Digital Signature
  • User puts message through hashing algorithm → digest
  • Digest encrypted with sender's private key → signature
  • Message + signature sent to receiver
  • Receiver decrypts signature using sender's public key → digest
  • Receiver hashes received document → second digest
  • Digests compared — if same, document is authentic
🔐 Two-Factor Authentication
  • Requires two forms of verification
  • e.g. password + SMS code
  • Prevents unauthorised access even if password stolen
🧬 Biometric Passwords
  • Uses unique biological features
  • e.g. fingerprint, retina scan, face ID
  • Hard to replicate
TOPIC 04 · §6.2
Validation & Verification
VALIDATION CHECKS · VERIFICATION METHODS · WHY DATA CAN STILL BE WRONG
VALIDATION

Checks data is reasonable/sensible — in the correct format, range, or type. Does NOT check accuracy.

VERIFICATION

Checks that data matches the original — is accurately entered. Does NOT check if original is correct.

VALIDATION CHECKWHAT IT CHECKS
Format checkData is in the required format (e.g. date as DD/MM/YYYY)
Length checkData contains the correct number of characters
Type checkCorrect data type entered (e.g. only numeric data)
Range checkValue falls within an acceptable range (e.g. 1–100)
Presence checkData has actually been entered (field not left empty)
Check digitFinal digit calculated from other digits — verifies no transcription error
Verification Methods
  • Visual check — manual comparison with source document
  • Double entry — enter twice, system compares both entries
Why Data May Still Be Wrong
  • Original document may be incorrect — verification only checks if it matches, not if it's correct
  • Validation only checks if data is reasonable — not if it's accurate
⚡ VALIDATION vs VERIFICATION  Validation = reasonable? Verification = matches original? Neither guarantees data is CORRECT — the original source could be wrong.
TOPIC 05 · §6.2
Parity Check & Checksum
ERROR DETECTION DURING DATA TRANSFER
Parity Check
  • Type of parity agreed before transfer (even or odd)
  • Each byte contains a parity bit
  • Receiver counts 1s in byte — checks parity matches
  • Parity block: additional parity byte sent with vertical AND horizontal parity
  • Intersection of error row/column identifies the error
  • ⚠️ Cannot detect if even number of bits changed (could cancel out)
Checksum
  • Checksum value calculated from data BEFORE transmission
  • Value transmitted along with data
  • Receiver recalculates checksum from received data
  • If checksums match → no error
  • If checksums don't match → error occurred
⚡ PARITY LIMITATION  "A parity check cannot detect an error if an even number of bits has been changed, as the errors may cancel each other out." This exact explanation = exam mark.

QUESTION 05
Explain three validation checks that could be used when a user enters a date of birth. [6]

MARK SCHEME (any 3 × 2)

  • Format check: ensures date entered in correct format e.g. DD/MM/YYYY (1) — rejects entry if format not followed (1)
  • Range check: ensures date falls within an acceptable range e.g. year between 1900 and current year (1) — rejects values outside this range (1)
  • Type check: ensures only numeric data entered for day/month/year fields (1) — rejects letters or symbols (1)
  • Presence check: ensures field is not left empty (1) — rejects blank entry (1)
◆ STANDARD
QUESTION 06
Describe how a checksum is used to detect errors during data transmission. [3]

MARK SCHEME

  • Checksum value calculated from the data before transmission (1)
  • Value transmitted along with data to receiver (1)
  • Receiver recalculates checksum from received data and compares — if different, an error has occurred (1)
★ CHALLENGE
QUESTION 07
Explain why validation and verification cannot guarantee that data entered into a system is correct. [4]

MARK SCHEME

  • Validation only checks if data is reasonable/in the correct format (1) — it does not check if data is accurate or correct (1)
  • Verification checks if data matches the original source document (1) — but if the original document is incorrect, the error will not be detected (1)
Examiner: Must address BOTH validation and verification limitations separately for full marks.
